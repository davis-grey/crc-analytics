# 🦁 Cork Royal Challengers — Cricket Analytics

A static, GitHub Pages–hosted cricket match and performance dashboard. No database, server framework, JavaScript build tool or paid hosting is required.

## What the app provides

- Club overview, season win/loss results and recent fixtures.
- **Automatically generated tournament cards**: matches, wins, losses, batting leaders, wicket takers and official CRC Player of the Match counts, all computed from match JSON.
- Match scorecards, over progressions, worm/Manhattan charts and ball-by-ball details.
- Player profiles, leaderboards, caps and an explainable MVP points formula.
- Social/WhatsApp match poster generation.
- Tournament and indoor/outdoor filtering.

## One source of truth

**Edit:** `data/matches/*.json` (one match per file), `data/tournaments.json` (tournament *metadata*), `data/players.json` (players and aliases), or `data/team.json` (club details).

**Do NOT manually edit:** `data.js` or `data/all_matches.json`. Both are generated by `python scripts/build_data.py` and are included in Git because GitHub Pages (and opening the HTML file locally) need them.

```text
Scorecard → AI extraction + manual review → data/matches/<match>.json
                                      └→ python scripts/build_data.py
                                                ├→ validation
                                                ├→ data/all_matches.json (generated)
                                                └→ data.js (generated)
                                                          └→ stats.js (cricket stats + MVP)
                                                                  └→ app.js (views + events)
```

The existing seven match JSON files are now complete canonical records. The previous three incomplete Nemo match records have been synchronised from the originally published `all_matches.json`; **no published match scores were changed**. Current MVP points and discipline honours are intentionally recalculated under v2.0; the old v1 snapshot is retained for reference.

## Updating scores or adding matches

1. Find / export the scorecard. Use the AI tool to **extract data into the existing match JSON structure**, not to change `app.js` or HTML. Never assume missing details; flag them for your review.
2. For an existing match, edit its file in `data/matches/`.
3. For a new match, create a draft skeleton (optional):
   ```bash
   python scripts/new_match.py --id autumn-cup-m1 --tournament csk-indoor-2026-s3 --date 2026-11-01
   ```
   Fill the resulting `_drafts/autumn-cup-m1.json` using your scorecard; compare runs, wickets, extras and legal balls, then move it to `data/matches/`. `_drafts/` is git-ignored.
4. **For a new tournament**, add one record to `data/tournaments.json`. `id` must match `tournamentId` in its matches. Record only editorial metadata there (venue, placement, format), **never hardcode player statistics**.
5. **For a new CRC player or scorer alias**, add an entry or alias in `data/players.json`. In particular, `Savio` and `Savio Lobo` have distinct IDs; do not conflate them.
6. Build, test and commit source JSON **plus both generated files**:
   ```bash
   python scripts/build_data.py
   python scripts/validate_data.py
   python -m unittest discover -s tests -v
   node tests/test_app.cjs
   node tests/test_mvp_v2.cjs
   ```
7. Push to your GitHub Pages publishing branch after review. The GitHub Actions workflow runs the same validation and regression tests on pushes and pull requests.

**The expected process for tournament #3:** New tournament metadata + its match JSON files + one build command. **No edits to HTML, `app.js` or `stats.js`**. For CricAce and Stumps instructions, see [SCORECARD_IMPORT.md](SCORECARD_IMPORT.md).

## Running locally

You can double-click `index.html` after running the build, or run:

```bash
python -m http.server 8000
```

Then open `http://localhost:8000/`. Scripts used by the browser are `data.js`, `stats.js` and `app.js`, with externally hosted libraries for Tailwind, icons, charts and posters. Internet is needed for those visual libraries, though the match data is local.

## Validation and rules

Validation **blocks** missing/duplicate match or tournament IDs, unknown CRC roster members, invalid cricket overs (such as `1.6`), missing core match fields, invalid outcomes, and inconsistent batting runs + extras / final over progression. It **warns** about discrepancies that may be legitimate scorer issues (e.g. substituted players, deliveries not matching displayed overs) without altering source data.

The previously flagged CSK 8-a-side lineups and no-ball deliveries were resolved using team-provided confirmation; see [`data/DATA_QUALITY.md`](data/DATA_QUALITY.md). Current datasets validate with no errors or warnings. Never change scorer data merely to silence a validator.

`tests/legacy_stats_snapshot.json` preserves archived v1.0 output and protects unchanged raw statistics and official POTM counts. Current v2.0 scores are independently audited from canonical JSON with exact rational arithmetic by `tests/mvp_v2_audit.py`; `tests/test_mvp_v2.cjs` compares every match/player and tests negative scores, milestones, multiple overs, precision and ties. Do not overwrite the historical v1 snapshot to hide intentional methodology changes.

## Code structure

- `stats.js`: Player identity resolution, cricket overs, per-match honors, season statistics and tournament aggregate highlights.
- `app.js`: Rendering, UI state, navigation, filtering, charts, profiles and poster generation.
- `index.html`: The visual shell. Mobile profile metrics and tournament statistic grids are responsive; tournament cards use consistent mobile/desktop padding.
- `scripts/data_pipeline.py`: Validation, reading single-source JSON and deterministic outputs.
- `scripts/new_match.py`: Unvalidated scorecard draft scaffold (not automated PDF/screenshot parsing).
- `.github/workflows/validate.yml`: Reproducible validation on GitHub.

## Current limits / next improvements

- **AI-assisted extraction is not automatic**: you still have to supply scorecards and review the resulting JSON. The previous `parse_stumps.py` contained no working parser and has been retired.
- The data model still stores player names in individual innings. Explicit player aliases resolve names to canonical roster records, but moving all references to immutable player IDs can be done as a separate, carefully tested migration.
- Much of the non-tournament UI remains in a large `app.js`. Extracting more view components, hardening HTML escaping throughout scorecards and bundling production Tailwind CSS would be reasonable later changes.
- Mobile changes were inspected from source and tested in browserless regression checks; **a complete live browser screenshot/device audit has not been completed**.

These constraints do **not** prevent you from adding a new tournament entirely through data.

## Statistical MVP v2.0

Current rankings use [CRC MVP v2.0](docs/MVP_METHODOLOGY.md): match scoring baseline, strike rate impact, runs saved impact, scheduled-over milestones, 20 points per bowler wicket, and final fielding weights (catch +8, run-out +12 once to the primary credited fielder, stumping +12). Statistical MVP and official POTM are distinct: **POTM adds zero MVP points**. Negative values are retained; only point displays round to one decimal. Season MVP sums unrounded match totals in the same central `stats.js` engine.

Top Batter/Bowler/Fielder use discipline impact. Orange/Purple Caps still use runs/wickets. See the [seven-match recalculation and season standings](docs/MVP_V2_RELEASE_REVIEW.md), including the Macroom run-out discrepancy. Historical scores, lineups and awards are unchanged. This is a review branch; production must not be merged until reviewed.

The proposed **Average MVP Points per Appearance** feature and **bowling achievement badges (2-wicket hauls, 2-wicket overs, 3-wicket hauls)** remain parked and unimplemented; these badges would add no MVP points. See [backlog](docs/BACKLOG.md).

For real mobile/desktop rendering checks, GitHub Actions runs `tests/test_mobile.cjs` at 320, 393, 430 and 1280 pixels. Playwright is installed only into the runner’s temporary test directory; there are no new application packages or runtime dependencies. The workflow uploads review screenshots without deploying the application.

### MVP Methodology page

Open `methodology.html` from desktop/mobile navigation, MVP rankings or the formula explanation. The approved content is in `docs/CRC_MVP_v2_Methodology_ASD_STE100_Style.md`. This source remains separate from the historical/internal methodology record. The page uses the existing dark palette, native expandable examples, a glossary and tables that scroll within the page on mobile. It needs no application data or Markdown runtime dependency.

After an approved documentation change, run `python scripts/build_methodology.py`. Check the committed page with `python scripts/build_methodology.py --check`. Tests require the source, rendered page and scoring engine to identify the same MVP version. Change scoring only through a separately approved formula update.
